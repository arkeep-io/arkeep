# 0029. Sync files between agents with Syncthing, hub-and-spoke

- **Status:** Proposed
- **Date:** 2026-11-27
- **Deciders:** Arkeep maintainers (proposed by @Presoon)

## Context

Users who back up several machines with Arkeep also want to keep directories
in sync between them (a PC, a laptop, a server), defined in the same panel and
run by the same agents. Sync is not backup: a deletion on one machine is
applied to the others. It is a second job for the same fleet.

Writing a sync engine has the cost and the risk that led to restic for backups
([0003](0003-restic-and-rclone-embedded-in-the-agent.md)): conflict handling,
renames, partial transfers and crash safety take years to get right, and users
want to keep their data usable without Arkeep. Syncthing does this well, with
an open protocol.

Syncthing is peer to peer: for two devices to sync, one must accept a
connection from the other, or both must go through public discovery and relay
servers. Arkeep agents never listen on a port and never contact anything but
their server ([0002](0002-server-agent-architecture-with-agent-initiated-grpc.md)).
A mesh of agents would break both rules on every machine. The machines to
sync are also rarely online at the same time.

## Decision

- Arkeep **orchestrates Syncthing**; it does not implement sync. The
  unmodified Syncthing binary is embedded in the agent like restic and rclone
  ([0003](0003-restic-and-rclone-embedded-in-the-agent.md)), pinned and
  verified against its signed release checksums
  ([0013](0013-pin-and-verify-every-dependency.md)). It is embedded in every
  agent, whether file sync is used or not: no download at run time and no
  second agent variant. Only
  `agent/internal/syncthing` may start or configure it.
- File sync is **opt-in per agent** (`ARKEEP_SYNC_ENABLED`). Without it the
  agent neither extracts nor starts Syncthing, advertises no sync capability,
  and the server never sends it a sync configuration.
- A **sync group** is laid out as **hub and spokes**:
  - a **spoke** holds the files. Its Syncthing has discovery, relays and NAT
    traversal turned off and listens on loopback only (Syncthing cannot run
    without a listener). Its only peer is the hub, which it dials over TCP;
  - the **hub** is an agent started as one on its own machine
    (`ARKEEP_SYNC_HUB_ADDR`). It is the only kind of agent that accepts sync
    connections (TCP 22000 by default). It stores every folder encrypted
    (Syncthing's *untrusted device*, folder type `receiveencrypted`) and
    relays it, so spokes sync without being online together.
- The hub is an **accepted exception** to "the agent never listens"
  ([0002](0002-server-agent-architecture-with-agent-initiated-grpc.md)): it is
  chosen by whoever runs that machine, and the server can neither turn an
  agent into a hub nor make a spoke listen.
- The server holds the model and sends each agent its **complete desired
  state** on the job stream (`JOB_TYPE_SYNC_CONFIG`), when the agent connects
  and whenever a group changes. The agent reconciles its Syncthing with it
  through Syncthing's REST API, bound to loopback, and reports folder states
  with `ReportSyncStatus`. The payload is defined once, in `shared/filesync`.
- Devices are **paired by the server**: an agent reports its Syncthing device
  ID when it registers, and the server hands it to the agent's peers.
- Folder passwords are generated by the server, encrypted at rest and never
  returned by the API ([0007](0007-encrypt-credentials-at-rest.md)). They are
  sent to spokes only, on the gRPC stream. The hub never receives one.
- Sync groups are written by **admins only**: a group makes an agent read and
  write a directory, the same trust class as a policy
  ([0009](0009-hooks-and-command-sources-run-on-the-agent-admin-only.md)).
- **Sync and backup are kept apart.** When the source path of a backup policy
  lies inside a directory the same agent syncs, the GUI warns that the same
  data may be backed up from every member, and the admin must acknowledge it
  before saving. It does not have to ship with the first version.

### Rules that protect the user's files

Every one of these is covered by a test and must stay so:

1. Arkeep never deletes, moves or overwrites a file of a synced directory.
   Removing a member or a group, changing a path and pausing only change
   Syncthing's configuration.
2. A new member is receive-only until it holds everything the group has.
3. A directory that already holds files joins only after an admin confirmed
   that they may be merged into the group.
4. When a member's path changes, the old location is forgotten before the new
   one is added, so files missing from the new directory are not read as
   deletions.
5. An agent that cannot reach its server keeps the last configuration it was
   sent. It never applies one it did not receive.
6. An agent that registers with a new Syncthing identity starts its
   memberships over (rules 2 and 3).
7. The agent's state directory cannot be synced.

## Consequences

- Spokes sync behind NAT with no port open. One inbound TCP port exists per
  hub, on a machine an admin picked for it.
- The hub stores a full encrypted copy of every group it serves, which costs
  disk space. If it is compromised, the attacker learns sizes and modification
  times, not names or contents. If the server is compromised, the folder
  passwords are exposed; it already controls the agents
  ([0009](0009-hooks-and-command-sources-run-on-the-agent-admin-only.md)).
- The hub is a single point of failure for sync, not for the files: while it
  is down every spoke keeps its copy and syncs again later.
- Every agent binary grows by about 35 MB, with or without file sync. The
  agent stays a single file that works offline and air-gapped, and releases
  keep one set of artifacts. If the size becomes a problem on small devices,
  it can be revisited with real numbers.
- Upgrading Syncthing requires a new agent release. Its pins are refreshed by
  the scheduled workflow that refreshes restic and rclone, with the hashes
  checked against Syncthing's signed release checksums.
- Syncthing is distributed under MPL-2.0. Arkeep ships the upstream binary
  unmodified, next to its own Apache-2.0 code.
- Sync is not backup, and the documentation and the GUI must say so. Concurrent
  edits are kept as `.sync-conflict` copies and reported.
- First version: one hub per group, which cannot be changed afterwards; ignore
  patterns and versioning are set per group; conflict files are found by
  walking the folder.
- Compliance is checked by an end-to-end test that runs the real Syncthing
  binary as a hub and spokes, and by the reconciler's table tests.

## Alternatives considered

- **Full mesh, Syncthing's default** — every endpoint must accept connections
  or use public discovery and relays, against
  [0002](0002-server-agent-architecture-with-agent-initiated-grpc.md).
- **A private relay (`strelaysrv`) next to the server** — no inbound port on
  agents and nothing stored on the server, but two machines only sync while
  both are online.
- **Our own sync engine** — far more work and risk, for the reasons given in
  [0003](0003-restic-and-rclone-embedded-in-the-agent.md).
- **`rclone bisync` on a schedule** — already embedded, but periodic rather
  than continuous, pairwise, and with no relay for machines that are never
  online together.
- **Download Syncthing on demand, or a second agent variant with sync** —
  saves about 35 MB for agents that do not sync, but adds a run-time download
  path that fails offline, or a second set of release artifacts (packages,
  images, the Home Assistant app).
- **A dedicated gRPC stream for the sync configuration** — the job stream
  already carries requests that are not jobs (volume listing, snapshot
  browsing); a second stream per agent adds connection state for no gain.
- **The hub as a separate component** — one more binary to ship, enroll and
  supervise, when an agent already has an identity and a channel to the
  server.
